# Hashroll architecture

How the code is organized, how the pieces talk to each other, and what happens during a bet.
For setup instructions, the full Provably Fair specification and known limitations, see the [README](../README.md).

---

## 1. The big picture

Hashroll is a provably fair casino (Dice, Plinko, Roulette) where **the Solana program holds the money and decides every outcome**. The backend never touches player funds and cannot fake a result; it only holds the house key that commits to and reveals the server seeds.

| Responsibility | Where it lives |
|---|---|
| Game rules and Provably Fair math | `packages/fair` (TypeScript) and `fair.rs` (Rust), kept identical |
| Bankroll, bets, payouts, outcome computation | The Anchor program in `solana/programs/hashroll` |
| Committing and revealing server seeds | `apps/api` (the "house") |
| Signing bets, reading state, animating results | `apps/web` |

## 3. Anchor in one page

The on-chain program is written with [Anchor](https://www.anchor-lang.com/), the standard Rust framework for Solana programs. A raw Solana program only receives a list of accounts and a byte buffer; everything else (decoding the instruction, checking each account's owner, signer and address, serializing state) is up to the developer, and a missing check is a classic vulnerability. Anchor generates that code from declarations:

| Anchor feature | What it does | Example in `lib.rs` |
|---|---|---|
| `#[program]` | Each public function becomes an instruction; arguments are Borsh-decoded automatically | `settle_bet(ctx, server_seed, next_commitment)` |
| `#[derive(Accounts)]` | Declarative account validation (`seeds`/`bump` for PDAs, `has_one`, `Signer`, `init`, `mut`) run before the handler | `SettleBet`, `PlaceBet`, `OpenPlayer` |
| `#[account]` | Typed on-chain state with an 8-byte type discriminator prefix | `Config`, `PlayerState` |
| `require!`, `#[error_code]` | Validation with named errors | `require!(ps.pending, HashrollError::NoPendingBet)` |
| `emit!` / `#[event]` | Structured events in the transaction logs | `BetSettled`, `BetPlaced` |
| IDL | A JSON description of the program, generated at build time | `solana/client/src/idl/` |

The IDL powers the TypeScript client (`@coral-xyz/anchor`), so the API and the web app call the program with typed helpers such as `program.account.config.fetch(...)` and `program.methods.claimExpired().accountsPartial({...})`.

The toolchain (Rust, Solana CLI, Anchor 0.32) runs inside the `solanafoundation/anchor` Docker image, so none of it has to be installed locally.

## 4. On-chain program (`solana/programs/hashroll`)

### Accounts

**`Config`**: one global PDA.

| Field | Meaning |
|---|---|
| `admin`, `pending_admin` | Admin key and two-step admin transfer |
| `house` | Key allowed to open players, commit and reveal seeds |
| `mint`, `vault` | HROLL token mint and the bankroll token account (owned by a program PDA) |
| `house_edge_bps` | Dice edge (Plinko and Roulette have the edge built into their payouts) |
| `max_payout_bps` | Max profit per bet = free bankroll × this / 10000 |
| `settle_timeout_secs` | After this, the player can claim the max payout |
| `paused` | Blocks new bets only; settlement and claims keep working |
| `reserved` | Sum of the max payouts of all pending bets plus unwithdrawn `owed` balances |

**`PlayerState`**: one PDA per player.

| Field | Meaning |
|---|---|
| `nonce` | Index of the next (or pending) bet |
| `commitment` | `SHA256(serverSeed)` for that bet; all zeros means the house must commit one |
| `pending` + `bet_*` | The pending bet: game, amount, Dice/Plinko/Roulette parameters, client seed, max payout, placement time |
| `owed` | Payouts credited when the player's token account was missing at settlement |

Field order in `PlayerState` matters: the API finds pending bets with a `memcmp` filter on `pending`, at byte offset 80 (8 discriminator + 32 player + 8 nonce + 32 commitment). The client exports this as `PENDING_OFFSET`.

### Instructions

| Group | Instruction | Signed by | Purpose |
|---|---|---|---|
| Admin | `initialize` | upgrade authority | Create `Config` and the vault |
| | `set_params`, `set_house`, `set_paused` | admin | Tune parameters, rotate the house key, pause |
| | `propose_admin` / `accept_admin` | admin / new admin | Two-step admin transfer |
| | `fund_house` / `defund_house` | admin | Move HROLL into / out of the free bankroll (never `reserved`) |
| House | `open_player` | house | Create a `PlayerState` with the first commitment |
| | `commit_seed` | house | Store the commitment for the next bet |
| | `settle_bet` | house | Reveal the seed, compute the outcome, pay |
| Player | `place_dice`, `place_plinko`, `place_roulette` | player | Escrow the stake and register the bet |
| | `claim_expired` | player | Collect the max payout after the timeout |
| | `withdraw_owed` | player | Withdraw payouts credited to `owed` |

## 5. Shared libraries

### `packages/fair`

The single source of truth for the math, with values as `bigint`:

- `hashServerSeed`, `verifyCommitment`, `computeDigest` (HMAC-SHA256 of `clientSeed:nonce` keyed by the server seed)
- Dice: `digestToRoll`, `isWin`, `payoutFor`, `resolveDice`
- Plinko: `PLINKO_TABLES`, `digestToPlinkoPath`, `plinkoPayout`, `plinkoMaxPayout`, `resolvePlinko`
- Roulette: `digestToRouletteNumber`, `rouletteMasks`, `chipPayout`, `rouletteMaxPayout`, `resolveRoulette`

The web app uses it for previews (multiplier, profit) and for the `/verify` page. Fixed test vectors in `index.test.ts` are replayed against `fair.rs` and against the deployed program, so the TS and Rust implementations cannot drift apart.

### `solana/client` (`@hashroll/program`)

Shared glue for the API, the web app and the tests: the typed IDL, `PROGRAM_ID`, PDA helpers (`configPda`, `vaultPda`, `playerPda`, `playerAccounts`), instruction builders (`placeBetInstruction`), account readers (`fetchPlayer`), bet history parsing from `BetSettled` events (`fetchBetHistory`), and HROLL formatting (`formatHroll`, `parseHroll`; 9 decimals).

## 6. The house (`apps/api`)

A small NestJS app. It is **stateless**: everything it needs is either on-chain or derivable from its secret.

| File | Role |
|---|---|
| `config.ts` | Reads `.env` (RPC URL, house key, `HOUSE_SEED_SECRET`, `SETTLER_ENABLED`) |
| `house/players.controller.ts` | `GET /house`, `POST /players/:addr/open`, `POST /players/:addr/dev/faucet` |
| `house/house.service.ts` | Signs transactions with the house key: open player, commit seed, settle, faucet; queries pending bets |
| `house/seeds.ts` | Derives each server seed deterministically: `HMAC_SHA256(HOUSE_SEED_SECRET, genesisHash:programId:player:nonce)` |
| `house/settler.service.ts` | The settlement loop |

**Settler loop.** Two triggers feed the same `sweep()`:

1. **Fast path:** a log subscription on the program. Any log line containing `Instruction: Place…` or `Instruction: ClaimExpired` triggers a sweep immediately.
2. **Safety net:** a sweep every 3 seconds, which catches anything missed (API restart, dropped websocket, failed transaction).

Each sweep settles every pending bet, then commits a seed for every player without a commitment. Sweeps never overlap; a trigger during a running sweep schedules one more.

Because seeds are derived and never stored, the API can restart at any time without losing anything, and it never reuses a seed across clusters or deployments.

## 7. The web app (`apps/web`)

Next.js 16 with Tailwind 4 and the Solana wallet adapter. The web app reads balances, bets and history **directly from the chain**; it calls the API only to open the account and for the dev faucet.

| Path | Role |
|---|---|
| `src/lib/useHashroll.ts` | Central hook: loads config, vault, player, balances and history; exposes `play`, `claimExpired`, `withdrawOwed`, `faucet` |
| `src/lib/solana.ts`, `src/lib/api.ts` | RPC connection / Anchor program, and the API client |
| `src/app/{dice,plinko,roulette}/page.tsx` | One page per game, built on `components/GameShell.tsx` |
| `src/games/*Stage.ts` | PixiJS scenes, mounted by `usePixiStage.ts`; Dice is a 2.5D 0–100 lane with a draggable gate |
| `src/app/verify/page.tsx` | Independent verifier: recomputes any bet with `@hashroll/fair` in the browser, no API call |
| `src/lib/sound.ts`, `effects.ts`, `fx.ts` | Sound and celebration effects |

The animation **only replays** the outcome read from the chain. A stage exposes `roll()` (spin while waiting) and `reveal(outcome, win)` (land on the real result).

Transactions are signed by the wallet but submitted through the app's own RPC, so the wallet's selected network does not matter.

## 8. Bet lifecycle, end to end

```
 Player (web)                    Program (Solana)                    House (API settler)
      │                                 │                                    │
      │ 1. connect wallet               │                                    │
      │── POST /players/:addr/open ────────────────────────────────────────▶ │
      │                                 │ ◀── open_player(SHA256(seed₀)) ──── │
      │                                 │                                    │
      │ 2. place_dice / plinko / roulette (clientSeed, expectedCommitment)   │
      │───────────────────────────────▶ │ stake → vault                      │
      │                                 │ reserve max payout                 │
      │                                 │ pending = true                     │
      │                                 │── log "Instruction: Place…" ─────▶ │
      │                                 │                                    │
      │                                 │ ◀── 3. settle_bet(serverSeed, ──── │
      │                                 │        nextCommitment)             │
      │                                 │ check SHA256(seed) == commitment   │
      │                                 │ outcome = fair(seed, client, nonce)│
      │                                 │ pay from vault (or credit owed)    │
      │                                 │ release reservation                │
      │                                 │ emit BetSettled, nonce += 1        │
      │                                 │                                    │
      │ 4. poll until nonce increases,  │                                    │
      │    read BetSettled, animate     │                                    │
```

### Step by step

1. **Open.** On connect, `useHashroll` calls `api.open(address)`. The house runs `open_player`, paying the rent and storing `commitment = SHA256(serverSeed₀)`. The call is idempotent.

2. **Place.** `play()` re-reads `PlayerState` so it uses the current `nonce` and `commitment`. It rejects the bet early if one is already pending or no seed is committed. It then builds the `place_*` instruction with:
   - a random `clientSeed`, which the player can edit;
   - the `expectedCommitment`.

   The wallet signs it. On-chain, the program:
   - checks that `expectedCommitment` matches the stored one, so the bet fails instead of silently using another seed;
   - transfers the stake to the vault;
   - computes the bet's **maximum payout** over every possible outcome and checks it against the profit cap;
   - adds it to `Config.reserved`.

3. **Settle.** The settler derives the seed for `(player, nonce)` and sends `settle_bet(serverSeed, nextCommitment)`. The program:
   - verifies `SHA256(serverSeed) == commitment`;
   - computes `HMAC_SHA256(serverSeed, clientSeed:nonce)` and resolves the game in `fair.rs`;
   - pays the player from the vault. If the player's token account is missing, the payout goes to `owed` and stays reserved, so closing the account cannot block a reveal;
   - releases the reservation;
   - emits `BetSettled`, which carries the now-public seed;
   - increments `nonce` and stores `nextCommitment`.

4. **Display.** The web app polls `PlayerState` every 500 ms until `nonce` increases, reads the bet from `BetSettled` via `fetchBetHistory`, and calls `stage.reveal(outcome, win)`. It then rotates the client seed.

5. **Timeout (unhappy path).** If the house does not settle within `settle_timeout_secs` (60 s locally), the player calls `claim_expired` and receives the **full maximum payout**. Withholding an unfavourable reveal therefore never pays off for the house.

6. **Verify.** Every history entry links to `/verify`, which recomputes the commitment check and the outcome locally from the revealed seed, client seed and nonce.

### Why nobody can steer the outcome

- The house commits to the server seed **before** it sees the client seed.
- The player picks the client seed **without** knowing the server seed.
- The commitment cannot change while a bet is pending, and `expectedCommitment` pins it at placement.
- The program, not the house, computes the outcome and refuses a seed that does not match the commitment.

## 9. How each outcome is computed

`n` = first 4 bytes of the digest, as a big-endian `uint32`.

| Game | Outcome | Payout |
|---|---|---|
| Dice | `roll = floor(n × 10000 / 2³²)` (0–9999) | `amount × (10000 − houseEdgeBps) / target` if `roll < target` (under) or `roll ≥ 10000 − target` (over) |
| Plinko | Bit `i` of the digest = 1 means right at row `i`; slot = number of right bounces | Fixed multiplier from `PLINKO_TABLES[rows][risk][slot]` |
| Roulette | `number = floor(n × 37 / 2³²)` (0–36) | Each chip covering `k` numbers via a 37-bit mask pays `amount × 36 / k` |

`BetSettled.outcome` holds the Dice roll, the Plinko path bits or the Roulette number.

## 10. Bankroll safety at a glance

- Only the program moves vault funds; the vault is owned by a program PDA.
- Every pending bet's max payout is reserved up front, and `defund_house` can never touch `reserved`.
- Each bet's maximum profit is capped at a fraction (`max_payout_bps`, 1% by default) of the free bankroll.
- Pausing stops new bets but never blocks settlement, claims or withdrawals.

## 11. Local development and tests

```bash
npm run build:program   # build the Anchor program in Docker (also runs fair.rs unit tests)
npm run dev:infra       # local validator
npm run deploy:local    # deploy, create HROLL, initialize and fund the house
npm run dev:api         # house + settler on :4000
npm run dev:web         # UI on :3000
```

| Command | Covers |
|---|---|
| `npm run test:fair` | Provably Fair vectors and a cross-check against `node:crypto` |
| `npm run test:program` | Program integration tests in LiteSVM |
| `npm test -w @hashroll/api` | Seed derivation and token account helpers |
| `npm run e2e:local -w @hashroll/program` | One live round per game against the local stack (`-- --expire` tests the timeout path) |

Restarting the `solana` container resets the chain; run `npm run deploy:local` again afterwards. Addresses stay the same because the dev keypairs are committed.
